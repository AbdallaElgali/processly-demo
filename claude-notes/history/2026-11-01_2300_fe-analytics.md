# FE: admin analytics from the backend metrics routes

Branch: `fe/analytics` (from main at `4a03610`).

## Goal
Replace the browser-side numbers of the admin overview (`hooks/AdminData.tsx`, from `GET /audit/projects`) with `GET /analytics/projects` and `GET /analytics/projects/{id}`: four views, pooled vs per-project average, honest nulls, per-project table and detail.

## Preconditions found
- `fe/export-build-fix` is merged into main (`4a03610`).
- BDA main has `33c3159` (branch `feat/project-metrics`, merged). **There is no branch `feat/metrics-views`.** BDA's `analytics.py` and its note describe the *older, single-view* contract (flat `tp/fp/fn/precision/recall/f1` per row, outcomes `coverage_gap` / `parameter_removed` / `unranked`, no `views`, no `never_asked`, no `avg_candidates`, no `blind_first` / `final_first` per parameter). The session brief's contract (four views) is not in the backend yet, so this branch is built against the brief's contract with fixtures, not against a running backend.

(Outcome section is added at the end of the session.)

## Outcome

### What changed for the user
The admin Projects view now opens on an analytics overview that reads only `GET /analytics/projects`: two large tiles ("Found by the AI" F1, "Right first time" F1) with the per-project average as the main number and the pooled value labelled underneath, avg. candidates on the "found" tile, acceptance rate (both values) and approved / not approved counts. A View switch (four views, default "Found by the AI") drives the precision / recall / F1 / correct-wrong-missed / avg. candidates tiles, the charts and the table. Charts show approved projects in `approved_at` order, "Last 5" (default) or "All", keyed by `project_id` (alias only in tick and tooltip formatters; tooltip shows alias, approval version, date, value; nulls are gaps, with an optional comparison line "Right first time"), plus a stacked origin-mix chart. The table lists all projects (approved first), sortable by every numeric column with null last, "not approved" rows without numbers, "left out" with a tooltip of the four parts. A row click opens the project detail (`GET /analytics/projects/{id}`): four views side by side, a parameter table with plain-word outcomes per view, matched candidate labels, and an outcome filter; 404 / 422 / other errors as plain messages. Info tooltips carry the help texts.
`hooks/AdminData.tsx` no longer computes F1, acceptance or the 5-project chart; it keeps the sidebar list and feedback. The per-project friction view (`GET /audit/project/{id}`) is untouched. `GlobalOverview.tsx` and its dashboard types are deleted.

### Contract differences found
- The brief names backend branch `feat/metrics-views`; it does not exist. BDA main contains `feat/project-metrics` (`33c3159`), whose `analytics.py` / note describe the **older single-view contract**: flat `tp/fp/fn/precision/recall/f1` per row (no `views`, no `avg_candidates`, no `scored`), `excluded` fields flattened (`coverage_gap`, `parameter_removed`, `unranked`; no `never_asked`), pooled/average without `views`, and per-parameter `blind_value/blind_unit/outcome` (one outcome; values `coverage_gap` / `parameter_removed` / `unranked` without the `excluded_` prefix; no `blind_first/final_first`, candidate counts, `matched_candidate`).
- So this branch is built against the brief's four-view contract, tested with fixtures, and **will not work against the backend as merged today**: the overview would fail on `views`. Not verified against a running backend or in the browser for that reason. When the backend ships the four-view contract, re-check `api/types/analytics.ts` against `analytics.py`.
