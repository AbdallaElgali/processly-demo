# Parameter / AI-Metric / Flag Refactor — Implementation Log

_Executed: 2026-06-16 16:58 WEDT_
_Branch: `audit`_
_Companion to: `parameter-flag-refactor-plan.md` (the analysis this implements)_

---

## Context

The backend changed in two ways, which unblocked the full refactor:

1. **`stream-specs` now persists candidates and auto-sets `selected_candidate_id`** to the first AI candidate — so what the user sees is already saved before they touch anything; the user only saves *their* changes.
2. **`GET /projects/{project_id}` now returns the full candidate list per parameter** via `FullProjectDetailsOutput` → `FullProjectParameterOutput.candidates: AiMetricCandidateOutput[]`.

This made **Option A** (persist + rehydrate candidates) from the plan possible: bounding boxes and AI alternatives now survive a save/reload cycle. All work below is **frontend-only**.

---

## Summary of the model change

**Before:** the frontend modeled a parameter as N candidate `Specification`s with one selected, but the DB modeled it as one resolved row + a separate flag-ticket table. Translation happened in four places with inconsistent rules; flags were written through two competing paths.

**After:** one canonical adapter owns all DB↔UI translation; `Specification` carries an explicit `candidateId`; confidence has one canonical scale; flags have a single write-path that persists immediately.

## Files changed

### 1. `types/index.ts` — domain model
- Added `export type ReviewAction = 'PENDING' | 'MODIFIED' | 'ACCEPTED'`.
- `Specification`:
  - Added `candidateId: string | null` — the real AI metric candidate id (null for human-entered values). `id` stays as the React/stable key (equals `candidateId` for AI candidates).
  - Documented `confidence` as canonical **0–100** (UI scale).
- `InputField`:
  - `isFlagged` is now a plain `boolean` (was `boolean | null`).
  - `activeFlagId` is now required `string | null`.
  - `reviewAction` is now typed `ReviewAction` (was `string`).
  - **Removed `prevFlagId`** (the fragile hand-rolled re-flag chaining).

### 2. `api/projects.ts` — response types
- Added `AiMetricCandidate` interface mirroring backend `AiMetricCandidateOutput` (snake_case; confidence on 0–1 scale).
- Added `candidates?: AiMetricCandidate[]` to `ProjectParameter`.
- `ProjectDocument` gained optional `path?` / `analyzed?` (match backend output).
- `Project` gained optional `title?` / `name?` — these were already referenced across pages/sidebars but never declared (pre-existing type errors; added to get a clean compile).

### 3. `lib/parameter-adapter.ts` — **NEW**, the single source of truth
Centralizes every DB↔UI conversion:
- `toUiConfidence` / `toBackendConfidence` — the only place confidence is scaled (×100 / ÷100).
- `formatBoundingBox` / `reverseFormatBoundingBox` — moved out of `analyze-document.ts`.
- `candidateToSpecification` — one mapper that handles **both** the SSE stream item shape (camelCase, nested `source`, `value`/`id`) and the persisted `AiMetricCandidate` shape (snake_case, flat `source_*`, `ai_value`). Guarantees they stay aligned.
- `dbParamToInputField`:
  - Builds `specifications[]` from `candidates` (restores bounding boxes + alternatives).
  - Selects the candidate matching `selected_candidate_id` (falls back to first).
  - If `is_human_modified`, surfaces the saved `final_value`/`final_unit` on the selected spec (confidence nulled) while keeping all candidates as alternatives.
  - If there are no candidates but a `final_value` exists, builds a single human spec from the param-level source fields.
- `inputFieldToParameterInput`:
  - `is_human_modified` derived from `reviewAction === 'MODIFIED'` (replaces the `confidence === null` heuristic).
  - `selected_candidate_id` = `activeSpec.candidateId` (the real candidate id, null for human values).
- `specsStreamToInputFields` — moved from `analyze-document.ts` (`mapSpecsToFields`), now uses `candidateToSpecification`.
- `mapFieldsToSpecs` — moved from `analyze-document.ts`; sends `spec.candidateId` as `id` (omitted for human specs so Pydantic generates a UUID), confidence via `toBackendConfidence`.

### 4. `api/analyze-document.ts`
- Stripped the inline mappers and bbox helpers (now imported from the adapter).
- Imports `specsStreamToInputFields` and uses it for `partial` / `refining` / `complete` events.
- Switched base URL to `config.api`.
- Removed the SSE debug `console.log`s (connection, per-event, done, payload).

### 5. `hooks/useAnalyze.ts`
- `mapFieldsToSpecs` now imported from the adapter (was from `analyze-document`).
- Removed dead `const x = 1; if (x == 1){ ... }` wrapper and stray `console.log`s.

### 6. `hooks/ParameterManager.tsx`
- `hydrateFieldsFromDB` is now a one-liner: `setFields(dbParameters.map(dbParamToInputField))`.
- `handleFieldChange` builds a human spec with `candidateId: null`.
- **`handleFlag` is now the single flag write-path:**
  - Resolves `candidateId` from the active spec (nullable).
  - On flag: calls `flagParameter(..., parent_flag_id = field.activeFlagId, ...)` and keeps the returned `newFlagId` as `activeFlagId` (fixes the bug where the new id was discarded).
  - On unflag: `unFlagParameter(activeFlagId, null, 'DISMISSED')`, clears state.
  - After updating local state, calls the injected `persist(nextFields)` so `human_flagged` is written to the DB immediately (durable in editor **and** review mode).
- Hook now accepts `{ persist?: (fields) => Promise<void> }`.
- Removed the now-unused `SCHEMA_GROUPS` / `FIELD_LABEL_MAP` (moved into the adapter).

### 7. `app/bda/page.tsx`

## Open caveats / assumptions (carried from the plan)
1. **Confidence scale**: assumed backend confidence is **0–1** (consistent with the stream path). If the DB stores 0–100, hydrated values will now be ×100 too high — confirm.
2. **Flag column sync**: since the backend was off-limits, the frontend persists `human_flagged`/`flag_reason`/`flagger_id` via the parameter PUT right after the ticket call. If the flag endpoint already syncs those columns, this is harmless redundancy. `ParameterInput` still does not carry `active_flag_id` — the frontend keeps it from the ticket response and from GET hydration.
3. **`review_action` values**: assumed `'PENDING' | 'MODIFIED' | 'ACCEPTED'`; `'ACCEPTED'` remains backend-owned (set via approve). Confirm the backend's accepted set.
4. **Streamed candidate ids == persisted candidate ids**: assumed the `id` streamed during `stream-specs` matches the persisted `ai_candidates.id`, so `selected_candidate_id` sent on save resolves. Backend detail to confirm.
